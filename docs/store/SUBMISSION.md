# Store submission runbook

End-to-end steps to publish **Mawa3id** (`com.mawa3id.app`) to Google Play and the
Apple App Store. Product code is complete; this is release engineering. Everything
here degrades cleanly — the repo builds and CI is green **before** you have store
accounts. Do the account setup, add the secrets, then run the lanes.

Related docs:
- Signing secrets & the build workflow: [`mobile/RELEASE_SIGNING.md`](../../mobile/RELEASE_SIGNING.md)
- Privacy-label answers: [`data-safety.md`](data-safety.md)
- Content rating: [`content-rating.md`](content-rating.md)
- Listing copy: `mobile/android/fastlane/metadata` and `mobile/ios/fastlane/metadata`
- Legal pages (served by the backend): `/legal/privacy`, `/legal/terms`

---

## 0. Prerequisites (you provide)

- **Google Play Developer** account (one-time fee) and **Apple Developer Program**
  membership (annual).
- A **production domain** with the backend deployed (Phase 7) serving `/legal/*`
  over HTTPS. Replace `REPLACE_WITH_YOUR_DOMAIN` in the iOS metadata
  (`support_url.txt`, `privacy_url.txt`) with it.
- The signing secrets from `RELEASE_SIGNING.md` (upload keystore for Android; App
  Store Connect API key for iOS), plus for metadata upload:
  - `PLAY_SERVICE_ACCOUNT_JSON` — a Play Console service-account key with the
    *Release manager* role (Play Console → Users and permissions / API access).
  - `APPLE_ID`, `APPLE_TEAM_ID`, `APP_STORE_CONNECT_KEY_ID`,
    `APP_STORE_CONNECT_ISSUER_ID`, `IOS_ASC_KEY_P8` (reused from signing).
- A **demo patient account** and a **demo doctor account** on the production
  backend for the reviewers (see §5).

## 1. Register the apps

- **Play Console** → Create app → package `com.mawa3id.app`. Category **Medical**;
  free; not a game.
- **App Store Connect** → Apps → New App → bundle id `com.mawa3id.app`
  (register the App ID with the **Push Notifications** capability first, per
  `RELEASE_SIGNING.md`). Primary category **Medical**.

## 2. Build the signed binaries

Add the Android + iOS signing secrets, then run the **Release build** workflow
(`release-build.yml`) via *Run workflow* or by pushing a `v*` tag. It produces:

- `android-release` — signed `.aab` (upload to Play) + `.apk`.
- `ios-release` — signed `.ipa` (upload to TestFlight / App Store).
- `android-screenshots` + `ios-simulator-screenshots` — real UI screenshots,
  en/fr/ar (generated by the screenshot harness — see §4).

Upload the first `.aab` to a Play track and the `.ipa` to App Store Connect
(Transporter, or let the release workflow's upload extend later). A binary must
exist on a track before a metadata-only push (§4) will succeed.

## 3. Fill the compliance forms (once, in each console)

- **Play Data Safety** and **Apple App Privacy** — copy the answers from
  [`data-safety.md`](data-safety.md). Key points: encrypted in transit, not sold,
  no tracking; **health data** and donation/purchase history are collected;
  payment card data is **not** (Stripe handles it); FCM token used only for
  messaging.
- **Content rating** — [`content-rating.md`](content-rating.md): IARC → Everyone;
  Apple → 4+. Declare user-generated content (reviews), digital purchases
  (donations), and Medical/Treatment information.
- **Privacy policy URL** — `https://<your-domain>/legal/privacy`. Set the support
  URL to `https://<your-domain>/legal`.

## 4. Push the store listing (copy + screenshots)

Listing text is version-controlled under `fastlane/metadata` (Play and App Store),
in `en-US`, `fr-FR`, `ar`. Screenshots are generated by the harness, not committed.

Run the **Store release** workflow (`store-release.yml`, manual dispatch). It:
1. regenerates the screenshots (emulator / simulator via `flutter drive`),
2. maps them into the fastlane screenshot folders, and
3. runs the fastlane lane for each platform whose secrets are present.

Leave **validate_only = true** for the first run (fastlane `validate` /
`supply --validate_only`) to check the metadata without publishing. Then re-run
with validate_only = false to upload.

You can also run a lane locally:

```bash
# Play (needs PLAY_JSON_KEY_FILE)
cd mobile/android && fastlane deploy
# App Store (needs ASC_KEY_ID / ASC_ISSUER_ID / ASC_KEY_P8, APPLE_ID, APPLE_TEAM_ID)
cd mobile/ios && fastlane deploy
```

### Images you must still supply by hand

- **Play feature graphic** — `1024×500` PNG at
  `mobile/android/fastlane/metadata/android/<locale>/images/featureGraphic.png`
  (not auto-generated).
- **Play icon** — `512×512` at `.../images/icon.png` (export from
  `mobile/assets/icon/app_icon.png`, or the real logo once it lands).
- Verify the generated screenshots meet each store's size rules (Play: phone
  16:9 / 9:16, ≥ 320px; Apple: 6.7" iPhone, and 12.9" iPad if offered on iPad).

## 5. Review notes (paste into each console)

> Mawa3id is a non-profit scheduling and communication tool for booking medical
> appointments. It does **not** provide medical advice, diagnosis or treatment.
> Medical records are authored by the treating doctor and visible only to that
> doctor and the patient. Donations are optional and handled by Stripe (not IAP).
>
> Demo accounts:
> • Patient — <email> / <password>
> • Doctor — <email> / <password>

## 6. Submit & roll out

- **Play**: promote the internal track → closed/open testing → production. Consider
  a **staged rollout**.
- **Apple**: attach the build, submit for review; use **phased release** once
  approved.

## 7. Updating

Bump `version:` in `mobile/pubspec.yaml` (e.g. `1.0.1+2`), update the changelog
(`changelogs/default.txt` for Play, `release_notes.txt` for Apple, all three
locales), rebuild via `release-build.yml`, and re-run `store-release.yml`.
